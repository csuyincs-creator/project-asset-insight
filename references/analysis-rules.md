# 项目分析规则

## 核心问题

最终必须帮助用户回答：

1. 这个项目到底是干什么的？
2. 它解决什么问题？
3. 它最核心的能力是什么？
4. 它大致怎么实现？
5. 哪些设计值得借鉴？
6. 哪些资产可直接复用？
7. 哪些资产适合改造后复用？
8. 哪些只需要借鉴思路？
9. 以后什么情况下应该重新打开它？
10. 如果只看 5～10 个文件，该看哪些？

## 阅读优先级

项目很大时，不逐文件阅读。优先级：

1. README / docs 首页
2. 顶层目录结构
3. 依赖声明
4. 核心入口
5. 核心模块
6. examples / demo
7. 配置
8. 必要的测试或文档

## 一句话定位

必须用普通语言重新解释项目，不照抄 README。

## 核心能力

提炼 3～10 个；功能很多时只保留真正核心能力。

## 架构分析

不要机械复制目录树。解释：
- 为什么这么分层
- 核心调用链是什么
- 扩展点在哪里
- 哪些抽象值得学

## 借鉴价值

“项目有这个功能”不等于“值得借鉴”。

每个借鉴点必须说明：
- 借鉴的具体是什么
- 适用于什么未来场景
- 是否需要复制代码

## 可复用资产

### A｜直接复用
独立脚本、工具函数、Prompt、Skill、Agent、组件、Schema、HTML/CSS、配置模板等。

### B｜改造复用
Adapter、Session、API Client、数据层、插件体系、任务调度、浏览器控制等。

### C｜思路复用
架构分层、模块边界、数据流、信息架构、交互方式、Agent 工作流等。

## 复用评价

对资产补充：
- 价值：高 / 中 / 低
- 复用成本：低 / 中 / 高
- 耦合程度：低 / 中 / 高

## 不要强行吹项目

允许结论：
- 参考价值低
- 只保留一个小技巧
- 无需深入研究
- 只保留笔记即可

## 本地运行信息

运行、测试、构建、Git 状态只作为辅助信息；不得成为正文主轴。
