# 项目分析规则

## 核心问题

最终必须帮助用户回答：

1. 这个项目到底是干什么的？
2. 它解决什么问题？
3. 它最核心的能力是什么？
4. 它大致怎么实现？
5. 哪些设计值得借鉴？
6. 哪些资产可直接复用？
7. 哪些资产适合改造后复用？
8. 哪些只需要借鉴思路？
9. 以后什么情况下应该重新打开它？
10. 如果只看 5～10 个文件，该看哪些？
11. 如果存在可视界面，它真实运行后长什么样，截图证据是什么？

## 阅读优先级

项目很大时，不逐文件阅读。优先级：

1. README / docs 首页
2. 顶层目录结构
3. 依赖声明
4. 核心入口
5. 核心模块
6. examples / demo
7. 配置
8. 必要的测试或文档

## 一句话定位

必须用普通语言重新解释项目，不照抄 README。

## 核心能力

提炼 3～10 个；功能很多时只保留真正核心能力。

## 架构分析

不要机械复制目录树。解释：
- 为什么这么分层
- 核心调用链是什么
- 扩展点在哪里
- 哪些抽象值得学

## 借鉴价值

“项目有这个功能”不等于“值得借鉴”。

每个借鉴点必须说明：
- 借鉴的具体是什么
- 适用于什么未来场景
- 是否需要复制代码

## 可复用资产

### A｜直接复用
独立脚本、工具函数、Prompt、Skill、Agent、组件、Schema、HTML/CSS、配置模板等。

### B｜改造复用
Adapter、Session、API Client、数据层、插件体系、任务调度、浏览器控制等。

### C｜思路复用
架构分层、模块边界、数据流、信息架构、交互方式、Agent 工作流等。

## 复用评价

对资产补充：
- 价值：高 / 中 / 低
- 复用成本：低 / 中 / 高
- 耦合程度：低 / 中 / 高

## 视觉项目的额外要求

只要项目存在 Web / GUI / Demo / Canvas / SVG / WebGL / 桌面界面等可视入口，最终分析不能只依赖源码推断。

必须在 TODO-09 按 `references/visual-verification-rules.md`：

- 实际打开可视界面
- 生成截图
- 记录运行证据
- 有视觉理解能力时重新读图
- 将源码结论与真实截图进行交叉确认

对于 UI / 交互 / 布局 / 可视化能力，优先写清楚：

- 源码证据在哪里
- 运行时截图证据是什么
- 两者是否一致
- 若不一致，以实际运行截图为高优先级事实，并说明差异

Agent 没有视觉理解能力时，不得声称截图“看起来正常”；只能引用机器级校验结果，并明确 `VISION_UNAVAILABLE`。

## 不要强行吹项目

允许结论：
- 参考价值低
- 只保留一个小技巧
- 无需深入研究
- 只保留笔记即可

## 本地运行信息

除 TODO-09 的最小化视觉验证外，运行、测试、构建、Git 状态只作为辅助信息；不得成为正文主轴。

视觉验证的目标是确认项目真实视觉资产，不是开展完整测试、修 Bug 或性能审计。
