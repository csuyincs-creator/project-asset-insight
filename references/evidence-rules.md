# 证据规则

## 结论类型

最终报告中的重要判断应区分：

- 文档明确说明
- 源码确认
- 配置确认
- Git/项目元数据确认
- 运行时确认
- 视觉截图确认
- Agent 推断
- 无法确认

## 证据优先级

对于 UI / 页面 / 布局 / 可视化 / 交互是否真实存在等问题，优先级建议为：

1. 运行时 + 截图确认
2. 源码确认
3. 配置 / 文档确认
4. Agent 推断
5. 无法确认

截图不替代源码；源码也不能替代真实视觉结果。两者应尽量交叉验证。

## 必须绑定证据路径的内容

以下内容尽量绑定实际文件或目录：
- 核心能力
- 核心架构
- 可复用资产
- 关键实现思路

建议格式：

**对应源码证据**
- `path/to/file`
- `path/to/module/`

对于存在可视界面的项目，还应补充：

**对应运行 / 视觉证据**
- `01-overview.png`
- `02-core-feature.png`
- `visual-evidence.json`

## 视觉证据状态

最终报告必须明确写出 `capture_status`：

- `CAPTURED`：已生成截图
- `NO_VISUAL_SURFACE`：确认项目不存在任何可视界面
- `CAPTURE_BLOCKED`：存在可视界面，但完成规定尝试后仍客观无法截图

若 `CAPTURED`，还必须明确视觉复核状态：

- `VISION_REVIEWED`：Agent 已实际查看截图
- `VISION_UNAVAILABLE`：Agent 没有视觉理解能力，但截图与机器级校验已经完成

禁止把 `VISION_UNAVAILABLE` 写成截图失败。

## 视觉判断的措辞边界

若 Agent 不具备视觉理解能力：

允许写：
- 截图文件已成功生成
- 截图尺寸为多少
- 浏览器命令退出码为 0
- DOM / Console / Network 自动检查结果

禁止写：
- 页面看起来正常
- 视觉效果优秀
- 没有遮挡
- 布局很合理

除非这些结论有机器可验证证据或 Agent 实际完成了视觉复核。

## 无证据时

若只能合理推断，明确写“推断”。

若无法确认，写“无法确认”。

禁止编造：
- 作者意图
- 商业模式
- 实际用户量
- 项目效果
- 用户当时为什么 Clone
- 用户是否真正使用过

对于“为什么可能值得保存”，只能写“可能的关注点”。
